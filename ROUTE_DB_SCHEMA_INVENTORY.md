# Инвентаризация выпущенных вариантов `Route.db`

Статус: подтверждено историей Git и instrumentation fixtures Room v1–v12;
реальные пользовательские БД не собирались  
Дата проверки: 2026-08-30

## Источники

- история `data_local/.../RouteDB.kt` до перехода с Room;
- история `data_local/build.gradle.kts` после перехода на SQLDelight;
- история `buildSrc/src/main/kotlin/Dependencies.kt` для номеров сборок;
- текущие `.sq`, `.sqm` и repair-код `DatabaseDriverFactory`.

В репозитории нет Git-тегов релизов. Поэтому соответствие ниже подтверждает состояние
кода в коммитах поднятия версии, но не доказывает, что каждая сборка была опубликована
в RuStore. Список фактически опубликованных APK/AAB нужно сверить с кабинетом RuStore.

## Проверенная текущая версия

В текущем дереве существуют `1.sqm`…`13.sqm`. Несмотря на оставшуюся в Gradle
настройку `version = 7`, сгенерированный `RouteDatabase.Schema.version` и фактический
`PRAGMA user_version` после миграции равны 14. Это подтверждено сборкой и
instrumentation-тестом на Android 16. Для runtime-проверок источником истины должен
быть `RouteDatabase.Schema.version`, а не дублированная константа.

Исторический `PRAGMA user_version = 7` всё равно не идентифицирует единственную
структуру. Возможны варианты с одинаковым номером 7:

- без/с `Passenger.isWorkStartByArrival`;
- без/с `BasicData.timeStartWorkBeforeArrival`;
- без/с `OtherWork`;
- без/с `RoutePartner`;
- до/после удаления `Train.isHeavyLongDistance`;
- без/с полями корзины и диагностическими таблицами.

Recovery reader обязан определять профиль через `sqlite_master` и
`PRAGMA table_info`, а `user_version` использовать только как один из сигналов.
Менять версию или набор миграций отдельно нельзя без новой согласованной миграции и
fixtures всех перечисленных вариантов.

## Проверенная матрица Room

Instrumentation-тест создаёт БД непосредственно из сохранённых Room schema JSON
версий 1–12, добавляет маршрут и по одной записи во все доступные дочерние таблицы
(`Locomotive`, `Train`, `Passenger`, `Photo`), затем мигрирует её текущим
production-кодом.
На Android 16 для каждой версии подтверждено:

- итоговая версия 14;
- успешная миграция как заполненной, так и полностью пустой БД;
- сохранение ID маршрута;
- сохранение количества записей каждой дочерней таблицы;
- наличие текущих полей корзины и диагностических таблиц;
- удаление legacy Room-колонок `Train.remoteObjectId` и
  `Locomotive.removeObjectId`;
- неизменность исходной БД при намеренно сломанной candidate-миграции.
- восстановление после сохранённой стадии `CANDIDATE_MIGRATING` и после стадии
  `SWAPPED`, эквивалентных остановке процесса до и после атомарной замены.
- сохранение маршрута, зафиксированного только в WAL до checkpoint: предмиграционный
  `wal_checkpoint(FULL)` переносит запись в согласованный backup и итоговую БД.
- повреждённая исходная БД и ранее существовавший backup не удаляются и не
  перезаписываются стандартным Android corruption handler.
- объёмный fixture из 500 маршрутов и 2000 дочерних записей сохраняет все route ID
  и количества по каждой дочерней таблице;
- ранее существующий legacy orphan не блокирует обновление всей базы и не приводит
  к появлению дополнительных orphan-записей.
- отсутствие обязательной исторической таблицы переводит запуск в recovery; такая
  база не принимается как успешно мигрированная.

Матрица обнаружила реальную несовместимость Room v1: в ней отсутствовала
`Train.distance`. Repair-код теперь добавляет её со значением `""`, которое является
текущим доменным default и сохраняет строковый контракт поля.

## Минимальный набор структурных fixtures

Это не синтетические «версии по догадке», а профили, непосредственно следующие из
подтверждённых изменений кода:

1. Room v1–v12 из сохранённых schema JSON — реализовано и проверено.
2. SQLDelight v5 из build 72/73.
3. SQLDelight v7 сразу после build 74.
4. v7 после добавления `Passenger.isWorkStartByArrival`.
5. v7 после добавления `OtherWork`.
6. v7 после добавления `RoutePartner`.
7. v7 после удаления `Train.isHeavyLongDistance`.
8. v7 с корзиной и диагностическими таблицами.

Для каждого профиля нужны варианты:

- пустая БД;
- один синхронизированный маршрут со всеми доступными дочерними сущностями;
- несинхронизированный маршрут;
- WAL с подтверждённой записью;
- повреждённая candidate-копия (исходник остаётся валидным).

## Что ещё нельзя считать подтверждённым

- какие версии до build 72 всё ещё установлены у реальных пользователей;
- точные схемы реально опубликованных APK, если release-коммит не совпал с AAB;
- максимальный размер пользовательской БД;
- наличие нестандартных схем после старых аварийных repair-путей.

Для закрытия этих пунктов нужны экспорт схемы без данных из тестовых устройств,
артефакты опубликованных AAB/APK либо обезличенная структурная телеметрия. До этого
importer должен быть fail-safe: неизвестный профиль не изменяет исходную БД и
переводит приложение в recovery mode.
