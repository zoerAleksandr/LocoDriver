# Задание: VK ID через access token (версия 3.0.4)

Релиз-блокер. Бэкенд и PWA уже готовы (см. «Что уже сделано»).
**Бэкенд деплоится первым, до публикации 3.0.4** — с
`VK_ALLOW_LEGACY_ID_AUTH=true` это безопасно для уже установленных версий,
зато новая версия сразу работает по проверенному пути.

## Зачем

`POST /v1/auth` с `methodAuth="vkId"` не проверяет пароль (это by design) и
до сих пор не проверял VK-токен вообще: сервер искал пользователя по
`auth_param` и сразу выдавал JWT. VK user id — публичное значение, видно в
адресе страницы `vk.com/id123456789`. То есть вход в чужой аккаунт «Машиниста»
сводился к подстановке чужого номера. Тем же способом через
`PATCH /v1/auth/vkId/add` можно было занять чужой номер, а через `vkId` в
`POST /v1/auth/create` — сразу зарегистрировать аккаунт с чужим VK.

Теперь user id выводит сервер: клиент присылает **VK access token**, сервер
меняет его на user id через `id.vk.com/oauth2/user_info`. Присланному
клиентом id сервер больше не верит.

## Контракт API

Все новые поля опциональные, старые не переименованы и не удалены — старый
клиент не ломается, пока на сервере включён переходный флаг.

### 1. Вход — `POST /v1/auth`

```jsonc
{
  "auth_param": "",             // при vkId игнорируется сервером
  "password": "",
  "methodAuth": "vkId",
  "vkAccessToken": "vk1.a....", // НОВОЕ: accessToken.token из VKID SDK
  "vkClientId": "<VKIDClientID>"// НОВОЕ: client_id приложения из secret.properties
}
```

Ответы:

| Код | detail | Что делать в UI |
|-----|--------|-----------------|
| 200 | — | обычный вход, `access_token` в теле |
| 401 | `vk_token_invalid` | «Не удалось подтвердить вход через VK ID» + повтор |
| 401 | `vk_access_token_required` | клиент устарел (флаг на сервере уже выключен) → «Обновите приложение» |
| 404 | `vk_user_not_found` | аккаунта с этим VK нет → флоу регистрации |
| 503 | `vk_unavailable` | «VK ID временно недоступен, попробуйте позже» |

Важно: **раньше «аккаунта нет» приходило как 401**, теперь по проверенному
токену это 404. Текущий код `authWithVKID` мапит 401 в «Неверная почта или
пароль», что для VK-входа бессмысленно, — переписать по таблице.

### 2. Регистрация — `POST /v1/auth/create`

```jsonc
{
  "login": "...",
  "email": "...",
  "password": "...",
  "vkAccessToken": "vk1.a....",  // НОВОЕ
  "vkClientId": "<VKIDClientID>" // НОВОЕ
}
```

Поле `vkId` теперь легаси: если пришёл токен, сервер пишет в `user.vk_id`
id из ответа VK, а присланный `vkId` игнорирует. Отправлять его не нужно.

### 3. Привязка — `PATCH /v1/auth/vkId/add`

```jsonc
{
  "token": "123456789",          // легаси, можно продолжать слать
  "vkAccessToken": "vk1.a....",  // НОВОЕ, именно из него берётся vk_id
  "vkClientId": "<VKIDClientID>" // НОВОЕ
}
```

`409 vk_id_already_linked` — этот VK уже привязан к другому аккаунту
(раньше в этом случае прилетала 500 из-за несериализуемого detail).

### 4. `PATCH /v1/auth/vkId/remove` — без изменений.

## Что менять в Android

Везде, где сейчас берётся `accessToken.userID.toString()`, нужен ещё и сам
токен — `accessToken.token`. Точки входа (`OneTap { onAuth = { _, accessToken -> … } }`):

- `ProfileScreen.kt:612` — миграционный экран, `registeredUserByVKIDForMigration`
- `ProfileScreen.kt:864` — привязка при ошибке загрузки VK-профиля, `attachVKID`
- `ProfileScreen.kt:907` — привязка / вход при уже привязанном VK,
  `onVkAuthForLinkedAccount` / `attachVKID`

Файлы:

1. **`data_remote/.../request/AuthRequest.kt`** — добавить
   `vkAccessToken: String? = null`, `vkClientId: String? = null`.
2. **`data_remote/.../request/AddVKIDRequest.kt`** — `token` сделать
   nullable, добавить те же два поля.
3. **`data_remote/.../request/RegisteredRequestByVKID.kt`** — убрать `vkId`
   из отправки (или оставить как есть — сервер его игнорирует при наличии
   токена), добавить `vkAccessToken` / `vkClientId`.
4. **`data_remote/.../AuthManager.kt`**:
   - `authWithVKID(vkId)` → `authWithVKID(accessToken: String)`, в запросе
     `auth_param = ""`, `password = ""`, `vkAccessToken`, `vkClientId`.
     Разложить коды ошибок по таблице выше (401/404/503 — разные состояния,
     не один текст).
   - `attachVKID(bearerToken, vkId)` → принимает access token, отдельно
     обработать 409.
   - `registerByVKID(vkId, email)` → принимает access token.
5. **`ProfileViewModel.kt`** — прокинуть токен во все вызовы
   (`authWithVKID`, `attachVKID`, `registerByVKID`,
   `registeredUserByVKIDForMigration`, `onVkAuthForLinkedAccount`).
   `secureTokenStorage.saveVkId(...)` по-прежнему хранит **id**, не токен, —
   он нужен только для локального признака «VK привязан».
6. **`client_id`** — уже лежит в `secret.properties` (`VKIDClientID`) и
   прокидывается через `vkidManifestPlaceholders` в `build.gradle.kts`.
   Пробросить его в код (`BuildConfig`-поле или строковый ресурс) и слать в
   `vkClientId`. Без него сервер переберёт allowlist и всё равно всё
   отработает, но лишним запросом к VK.
7. **`Dependencies.kt`** — `version_code = 81`, `version_name = "3.0.4"`.

**Access token нигде не сохранять.** Он нужен ровно на один сетевой запрос;
в `SecureTokenStorage` его класть не надо, в логи и Sentry — тем более.

## Отдельно: регистрация через VK

Сейчас `registerByVKID` отправляет `password = ""`, то есть у аккаунта нет
пароля и VK становится единственным способом войти. В PWA сделано иначе:
после «аккаунта с этим VK нет» пользователь заполняет email и пароль, и VK
привязывается к нормальному аккаунту.

Для 3.0.4 это **не обязательно** — можно оставить текущее поведение, задача
не про это. Но стоит завести отдельным пунктом: аккаунты с пустым паролем
нельзя восстановить, если VK-привязка отвалится.

## Проверить перед сборкой релиза

- [ ] Вход по VK на аккаунте с привязанным VK → 200, вход проходит.
- [ ] Вход по VK на аккаунте без привязки → 404, показывается флоу
      регистрации, а не «Неверная почта или пароль».
- [ ] Привязка VK в профиле → `user.vk_id` заполнен id **из ответа VK**
      (сверить с id страницы тестового аккаунта).
- [ ] Привязка VK, который уже привязан к другому аккаунту → 409 и внятный
      текст, а не молчаливый лог.
- [ ] Отвязка VK работает как раньше.
- [ ] Вход по email/паролю не задет.
- [ ] Уже залогиненный пользователь (валидный JWT) не разлогинивается: в
      токенах, их подписи и сроке жизни ничего не менялось.
- [ ] Сборка проверена против бэкенда из ветки
      `security/vkid-token-verification` (локально или на стенде), а не
      против прода — на проде правки ещё нет.

## Порядок релиза (не нарушать)

1. Бэкенд деплоится первым, с `VK_ALLOW_LEGACY_ID_AUTH=true` — версии 3.0.3
   и старше продолжают входить и регистрироваться по-старому.
2. Android 3.0.4 собран, проверен против бэкенда, **опубликован** в сторах и
   раскатан. Сервер к этому моменту уже проверяет токен, поэтому первые же
   пользователи новой версии идут по проверенному пути, а не по legacy.
3. PWA выкатывается после бэкенда.
4. Через 2–4 недели, когда в логах бэкенда счётчик
   `VK legacy id auth used` близок к нулю, флаг выключается — дыра
   закрывается. После этого пользователи на 3.0.3 и старше при входе через
   VK получат `401 vk_access_token_required` и должны обновиться.

Флаг на шаге 1 обязан быть `true` (значение по умолчанию). Деплой с
выключенным флагом до того, как 3.0.4 разойдётся по пользователям, полностью
лишит доступа всех, кто зарегистрирован через VK — у них пароль пустая
строка, и VK единственный способ войти.
