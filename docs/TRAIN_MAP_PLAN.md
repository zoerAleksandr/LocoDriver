# Карта в разделе «Поезд» — план и задание оркестратору (07–08.10.2026)

Статус: проект, не реализовано. Только Android (в вебе нет фоновой геолокации; PWA/iOS — позже). Эталон поведения — `SCREEN_SPECS.md` §6.9 «Карта поезда». Роль оркестратора, жёсткие правила и рабочий цикл — как в `docs/ORCHESTRATOR_map_parity.md` (сам код не пишет; исполнители — новые сессии/агенты в отдельных worktree; не пушить и не деплоить без явной команды; контракт сервера не менять; новых зависимостей без согласия нет; в коммитах Android-репо без Co-Authored-By; правка экрана — одним коммитом со спекой).

## Что хочет пользователь
Экран «Поезд»: в нижней панели кнопка «Станция» уменьшается, рядом появляется иконка «Карта» (та же карта и компонент, что при построении плеч). Содержимое карты по состоянию:
1. Ничего не заполнено — пустая карта с текущим местоположением.
2. Выбрано только плечо, у него есть координаты станций и построенный маршрут — маршрут тонким пунктиром как будущий путь.
3. Координаты станций или маршрут не определены — на карте предложение «Определить координаты по GPS»; результат сохраняется в справочник станций (§17.4).
4. Поезд уже едет по плечу — пройденный путь жирной линией, текущая скорость.
5. При включённом «АВТО» в точках следования пишутся время и скорость; тап по любой точке пройденного пути — время и скорость в этой точке.
6. Остановки — точки; тап — время прибытия и отправления.
7. Тап по точке маршрута впереди — расстояние до неё (км), ввод планового времени прибытия, расчёт средней скорости, нужной чтобы прибыть вовремя.

## Этапы (каждый — отдельный исполнитель, свой коммит, приёмка оркестратором, Ж-проверка на эмуляторе с тестовым поездом TEST-MAP, который удаляется)
0. **Спека и решения** (оркестратор): §6.9 в SCREEN_SPECS.md, решения по хранению трека (ниже), таблица паритета, строки 50+ в `docs/MAP_PARITY.md`.
1. **Каркас карты поезда:** кнопка «Карта» в нижней панели (кнопка «Станция» уменьшена), экран/шторка карты на общем компоненте карты плеч, текущее местоположение, состояние 1 и 3 (определить координаты → справочник).
2. **Будущий маршрут:** состояние 2 — пунктир по маршруту плеча с сервера (всегда запрос, кэш — запас без сети), станции плеча точками; «ближайшая впереди».
3. **Хранилище трека (локальное):** таблица SQLDelight (миграция БД! согласовать), точки {поезд, время, lat, lon, скорость, точность}, прореживание, лимит срока хранения; запись только при включённом «АВТО» (использует `GpsRecorder`, коммит 51200d5a+). Не уходит на сервер, не логируется.
4. **Пройденный путь:** жирная линия, цветовая шкала по скорости, текущая скорость, тап по точке → время и скорость; остановки точками (прибытие/отправление из станций поезда и стоянок без названия).
5. **Планирование прибытия:** тап по точке впереди → км до неё по маршруту, ввод времени (по `displayTimeZone()`), расчёт требуемой средней скорости, сравнение с текущей (успеваю/не успеваю).
6. **Полировка:** офлайн-тайлы, тёмная тема, контраст, доступность, тексты ошибок, обновление спеки и таблицы, итоговая Ж-проверка.

## Решения, нужные от пользователя до этапа 3
- **Хранение трека противоречит прежней записи «точки не хранятся».** Предложение: локально на устройстве, привязка к поезду, прореживание (точка раз в ~5 с в движении / раз в минуту на стоянке), срок 30 дней или пока существует поезд. Пользователь дополнительно хочет историю на сервере (см. раздел выше) — отдельный дизайн.
- Трек доступен только при включённом «АВТО»? (Предложение: да; без «АВТО» только будущий маршрут и текущее местоположение.)
- Перенос навигатора (ветка feature/navigator, §33) делаем кусками: `GpsRecorder` уже общий; карта/трек/скоростная шкала из навигатора — переиспользуем по мере этапов, ветку целиком в master не сливаем.

## Решения пользователя по идеям (08.10.2026)
**В работу:**
- Ожидаемое время прибытия и расстояние до следующей станции (лента над картой, обновляется в пути).
- **График скорости — отдельным экраном** (на телефоне под картой места нет): скорость по времени/пути, станции нанесены на график, масштабирование и прокрутка (zoom/pan); тап по точке графика подсвечивает её на карте и наоборот.
- Режим «еду по карте»: центрирование и поворот по ходу, крупная скорость.
- Планирование прибытия в точку впереди (из основного списка, этап 6).
**На будущее:** опережение/отставание от плана цветом линии (нужно хранить перегонное время хода; пока только при заданном плановом прибытии в конкретную точку); превышение ограничений скорости (нужны жд-километражи); экспорт трека и ссылка на точку.
**Не делаем:** длительность стоянки рядом с точкой; подсказка «пропущена станция X».
Остальные идеи из первого списка (предупреждение об автовыключении «АВТО» и т.п.) — по отдельному решению.

## Хранение треков и история на сервере (запрос пользователя)
Пользователь хочет хранить записанные треки не только локально, но и на сервере — чтобы смотреть историю работы. Это **изменение контракта и серверной БД** (новые эндпоинты/таблицы, миграция), плюс персональные данные (геолокация): перед работой нужен отдельный дизайн и согласование — объём (точка/5 с ≈ 17 тыс. точек за 24 ч смена; пакетная отправка, сжатие), срок хранения, удаление вместе с поездом/по запросу пользователя, доступ только владельцу (проверка владельца, как в `route.py`), шифрование/ограничение доступа администраторов, обновление политики конфиденциальности, согласие в приложении, отсутствие координат в логах, лимиты запросов. Старые клиенты не затрагиваются (новые эндпоинты). Этапы: 3 — локальное хранилище; 3а — серверная часть (дизайн → миграция → API → выкладка ДО клиента); 3б — отправка треков клиентом (фоном, при сети, по завершении поездки) и экран «История» (список поездок/смен, просмотр трека). Начинать 3а только после согласования дизайна с пользователем.

## Решения по хранению (08.10.2026)
- **Срок:** 180 дней (пока), далее удаляется автоматически; **избранные треки не удаляются** автоматически.
- **Согласие:** треки хранятся (в т.ч. на сервере) ТОЛЬКО с явного согласия пользователя; без согласия — не храним и предупреждаем («Трек не будет сохранён: нет вашего согласия»). Согласие отзывается в Профиле/Настройках; при отзыве серверные треки пользователя удаляются.
- **Объём:** сжатие и отправка пакетами (по окончании поездки, фоном, при сети; повтор при сбое).
- **История и удаление пользователем:** треки показываются карточками списка (дата, плечо/маршрут, длина, длительность, мини-карта) до открытия; удаление свайпом или иконкой корзины (с подтверждением); кнопка «В избранное» (звезда) — трек не удаляется через 180 дней.
- **Кто видит:** рекомендация — владелец; администратор кабинета НЕ видит сырые треки пользователей, а только обезличенный вклад (высотный профиль, см. ниже) без привязки к аккаунту. Доступ администратора к конкретному треку — только по запросу самого пользователя в поддержку. Окончательно за пользователем.
- **Высоты для режимной карты (новое требование):** при включённом «АВТО» собирать высоты профиля пути (GNSS-высота и, если есть датчик, барометрическая) вместе с точками; это вклад в построение режимной карты (кабинет `/admin/advisor`: серверная модель трека уже содержит точки `[tMs, lat, lon, speedKmh, altitudeM, baroAltitudeM|null, accuracyM]`, профиль строится в `advisor_profiles.py`). Отдельное согласие на «передавать обезличенные высотные профили для режимной карты»; передача без привязки к user_id, только фрагменты по участкам. Серверные эндпоинты и модель трека из ветки навигатора/кабинета — переиспользовать, не дублировать; контракт согласуется отдельно.

## Согласие: два независимых переключателя (решение 08.10.2026)
Экран согласия при первом включении «АВТО» (и позже в Настройках → «Данные и конфиденциальность»), без предустановленных «галочек»:
1. **«Сохранять мои треки и историю поездок»** — по умолчанию ВЫКЛ. Треки хранятся 180 дней (избранные — без срока); при выключении/отзыве серверные треки удаляются; без согласия «АВТО» работает как раньше (запись стоянок/отправлений), трек не сохраняется, пользователь предупреждён: «Трек не будет сохранён: нет вашего согласия».
2. **«Передавать обезличенные высоты для режимной карты»** — отдельно, формулировка без слов «трек» и «координаты». Передаются только пары «километр оси + высота» без времени, координат и идентификатора пользователя; клиент сам привязывает точки к оси.
Состояние и время согласия хранятся на устройстве и на сервере (для удаления/отзыва); политика конфиденциальности обновляется.

## Порядок реализации
Этап 1 (каркас; идёт) → 2 (пунктир) → 3 (локальный трек + согласие №1) → 3а (серверный дизайн и API, выкладка ДО клиента) → 4 (пройденный путь, скорость, остановки, график отдельным экраном, режим «еду по карте») → 5 (планирование прибытия, ETA и расстояние до следующей станции) → 3б (отправка пакетами, история/избранное/удаление) → 3в (согласие №2 и высоты) → 6 (полировка). Каждый этап — отдельный исполнитель в своём worktree, отчёт ≤30 строк; оркестратор принимает по диффам и тестам.

## Решения по рисованию пройденного пути (08.10.2026)
- Маршрут (будущий и пройденный) — только по рельсам: пройденный путь привязывается к рельсовой линии маршрута (map-matching), пока боковое отклонение GPS-точки ≤ **50 м** (было 30 м в этапе 4a — поднять); при большем отклонении рисуется сырая линия с пометкой «вне путей» (чип/подпись на карте). Время и скорость в тапе — из исходных точек. Реализовать в этапе 5 (или отдельной правкой после результата теста «трек по рельсам»).
- Карта следует за положением (сделано в 4a); режим «еду по карте» (крупная скорость, поворот по ходу) — этап 4в.
