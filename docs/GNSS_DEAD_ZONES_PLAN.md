# Зоны без GPS — план (общая карта + локальный слой)

Статус: **локальный слой и детектор реализованы** (ветка `feature/gnss-dead-zones`, SCREEN_SPECS §6.9 «Зоны без GPS»). Общая карта: сервер готов (раздел 12, ветка `feature/gnss-dead-zones-server`, не задеплоен), клиент (вклад, показ серверных ячеек, согласие №2 в редакции 2) — ветка `feature/gnss-zones-client`, SCREEN_SPECS §6.9.
Опора: `docs/TRAIN_TRACKS_SERVER_DESIGN.md` (согласие №2 «км оси + высота», `axisHash`/`offsetM`, обезличенный вклад без `user_id`), `GnssQualityMonitor`/`GnssQuality`, `TrackAnalysis.dataGaps`.

## 1. Что хотим

Красноватые мягкие пятна на карте поезда там, где у машинистов пропадает GPS или его глушат (пример: станция Кириши). Два источника на одной карте:
1. **Локально** — из своих треков (`Track.db`): работает офлайн, без подписки, без согласия №2.
2. **Общая карта** — обезличенные агрегаты по ячейкам от всех машинистов, под согласием №2.

Детектор «трек → плохие участки → ячейки» один на оба источника (`domain/gnss/GnssDeadZones.kt`, тесты `GnssDeadZonesTest`).

## 2. Детектор (готов)

Признаки на прореженном треке (в движении точка раз в 5 с, на стоянке раз в 60 с — это учтено в порогах):
- `GAP`: разрыв > 30 с (предыдущая точка в движении/скорость неизвестна) или > 90 с (предыдущая — стоянка); > 20 мин не считается (другой сеанс, телефон выключен).
- `POOR_ACCURACY`: точность хуже 50 м на отрезке ≥ 15 с (единичный плохой fix игнорируется; холодный старт в начале трека игнорируется).
- `SPEED_JUMP`: смещение ≥ 300 м со скоростью > 300 км/ч, заявленная скорость > 250 км/ч, либо рывок скорости ≥ 40 км/ч быстрее 11 км/ч/с.
Координаты плохих точек не используются (при спуфинге они ложные) — только достоверные опорные точки до и после участка.

## 3. Модель данных — рекомендация: фиксированная сетка ≈250 м

Ячейка = `(iy, ix)`: `iy = floor((lat + 90) / 0,00225°)`, шаг по долготе — целые микроградусы `round(2250 / cos(широта центра строки))`, `ix = floor((lon + 180)·1e6 / шаг)`. Одинакова на клиенте, сервере, PWA и iOS (тест-векторы — в `GnssDeadZonesTest`, перенести на сервер и в PWA).

Почему сетка, а не «ось участка (`axisHash` + км)»:
| | Сетка 250 м | Ось (`axisHash` + км, как высоты) |
|---|---|---|
| Покрытие | вся сеть с первого дня | только опубликованные участки кабинета; Кириши могут не попасть |
| Зависимость от сервера при детекции | нет (чистая функция, офлайн) | нужен кэш осей, смена `axisHash` → 409 и пересборка |
| Разрыв записи | хорда между двумя достоверными точками → ячейки; ось не нужна | разрыв проецируется на ось — на параллельных путях/развязках неоднозначно |
| Текст согласия №2 («только км пути и высота, без координат») | **нужно менять**: ячейка 250 м — это грубая координата | остаётся верным дословно |
| Приватность | ячейка ≈ участок пути в 250 м, без времени и порядка | чуть лучше (только км на оси) |

Размер: 100 м — мельче шума GPS и погрешности хорды (пятна дробятся, вклад легче сопоставить с маршрутом); 500 м — станция и перегон сливаются, пятно «Кириши» размывается. 250 м — компромисс. Если решение будет «строго ось» — детектор и тесты не меняются, меняется только `cellsOf` (проекция на ось вместо сетки) и контракт ниже.

## 4. Достоверность («порог показа»)

Сервер не знает, кто прислал вклад (нет `user_id`), поэтому «разные люди» нельзя посчитать по аккаунту. Решение:
- Клиент шлёт в каждом вкладе случайный `tag` (UUID, создаётся на устройстве, **не связан с аккаунтом**, ротируется раз в 30 дней). Сервер хранит `tag_hash` = первые 16 байт SHA-256(tag) и никогда не пишет его рядом с `user_id` и в логи. JWT нужен только как защита от спама (как у `altitude-contrib`).
- Таблица сырья `gnss_zone_report(iy, ix, tag_hash, kinds, day)`, уникальный ключ `(iy, ix, tag_hash)`: повторная отправка той же поездки и несколько проездов одного устройства считаются **один раз**; обновляются `kinds` и `day`.
- Ячейка попадает в карту, если за последние 90 дней `COUNT(DISTINCT tag_hash) ≥ 3` **и** отчёты были минимум в 2 разных календарных дня (`day`). Одиночный плохой телефон (или один человек) ячейку не создаёт; разовый эпизод за одни сутки не создаёт.
- Уровень пятна по числу разных устройств: 3–5 — слабое, 6–15 — среднее, > 15 — сильное. Точное число клиенту не отдаётся (только уровень) — k-анонимность.
- Старение: окно 90 дней; сырьё чистится через 120 дней; пересчёт агрегата `gnss_zone_cell` раз в 15 мин.
- Известное ограничение: нет знаменателя «проехали чисто». Постоянный тоннель/выемка тоже станет зоной — это честно «нет GPS» (в тексте не утверждаем «глушение»). Знаменатель потребовал бы слать «хорошие» ячейки = весь маршрут пользователя; не делаем (решение 3).
- Накрутка (несколько аккаунтов): rate limit на пользователя в памяти (как `SlidingWindowRateLimiter`) — ≤ 20 вкладов и ≤ 2000 ячеек в сутки; ручное скрытие ячеек в `/admin`.

## 5. Эндпоинты (новые, аддитивные; старые не меняются)

Миграция новая (две таблицы `gnss_zone_report`, `gnss_zone_cell`, `IF NOT EXISTS`, `id` ревизии ≤ 32 символов), **накатывать ДО деплоя кода**, как у остальных.

`POST /v1/gnss/zones/contrib` (JWT, camelCase)
```
{ "contribId": "uuid",            // детерминированный от сеанса — повтор = duplicate
  "tag": "uuid",                  // случайный, ротация 30 дней
  "step": 1,                      // версия сетки (0,00225°)
  "cells": [ {"iy": 40133, "ix": 123456, "kinds": 3} ] }   // kinds: битовая маска GAP=1, POOR=2, JUMP=4
→ 200 {"accepted": true, "duplicate": false}
```
Лимиты: тело ≤ 64 КБ, `cells` ≤ 1000, ячейки проверяются на допустимый диапазон `iy/ix`; 422 (без эха входных значений), 429, 401. Времени и координат в теле нет; сервер пишет только день приёма (`received_on`).

`GET /v1/gnss/zones?minLat=&minLon=&maxLat=&maxLon=` (**JWT обязателен** — решение 5)
```
→ { "step": 1, "updatedAt": 1760000000000, "cells": [ {"iy": ..., "ix": ..., "level": 1|2|3, "kinds": 3} ] }
```
Лимиты: bbox не больше 1°×1° (иначе 422), ≤ 5000 ячеек в ответе (иначе 422 «уменьшите область»), `ETag`/`If-None-Match` → 304, gzip, 60 запросов/час на пользователя. Отдаётся только то, что выше порога.

Кабинет `/admin/gnss`: список ячеек с уровнем, кнопка «скрыть» (флаг `hidden`), без доступа к сырью по устройствам.

## 6. Анонимность

- В вкладе нет `user_id`, времени (только день приёма на сервере), точных координат (ячейка 250 м), порядка ячеек (множество, перемешано), длительностей, скорости, номера поезда/рейса.
- Вклад содержит только **плохие** ячейки (обычно единицы за сеанс); «хороших» (маршрут) не отправляется.
- `tag` ротируется и не хранится рядом с аккаунтом; JWT проверяется и забывается. Отозвать отправленное нельзя (как высоты) — прямо сказать в тексте согласия.
- Чувствительность самих данных: публичная карта глушения может показывать расположение объектов, которые глушат. Поэтому `GET` только для вошедших и без точного числа (решение 5).
- Логи: только число ячеек и код результата; координат/ячеек/`tag` в `LogManager` не писать.

## 7. Хранение на клиенте

- **Локальные зоны** (сделано): считаются на лету по `Track.db`, кэш спанов в памяти процесса (по `trackId` + числу точек). Работает, пока треки существуют (согласие №1, срок 180 дней).
- **Серверные ячейки**: файловый кэш `cacheDir/gnss_zones/<плитка 0,5°×0,5°>.json` + `ETag`, обновление не чаще раза в 24 ч при открытии карты с включённым слоем и сети; офлайн — показ кэша. Объединение с локальными по ячейке: `level = max`, в карточке «Ваши поездки: N» из локальных.
- **Очередь вклада**: детект по потоку GPS в памяти на время сеанса «АВТО» (как `AltitudeSessionBuffer`, не зависит от №1 и не пишет в `Track.db`; поток сначала прореживается `TrackThinner`), по окончании — файл `filesDir/gnss_contrib/<sessionId>.cells`, `WorkManager` только при сети, backoff 1 мин, до 8 попыток; файл > 7 суток удаляется; отзыв №2 удаляет файлы.
- Схему `Track.db` не менять. Отдельный локальный реестр зон (чтобы зоны жили дольше 180 дней и существовали без №1) — опция, потребует новой БД/таблицы (решение 6).

## 8. Тексты UI

Локальная карточка (уже в приложении): «Здесь пропадал GPS» / «Замечено в N поездках» / «Нет данных GPS (до 4 мин)» / «Последний раз дд.мм.гггг» / «По вашим записанным поездкам. Причина неизвестна: глушение, тоннель, выемка или сбой телефона.»
Общая карточка: «Здесь часто пропадает GPS» / «Уровень: слабый | средний | сильный» (за последние 90 дней, у разных машинистов) / «Ваши поездки: N» (если есть) / «Данные обезличены и собраны по поездкам других машинистов. Причина неизвестна: глушение, тоннель, выемка или сбой телефона.»
Согласие №2 (новая формулировка, дословно согласовать): «Передавать обезличенные данные для карты: высоты пути и места, где пропадает GPS. Передаются километр пути, высота и участок карты около 250 м — без времени, без вашего имени и без маршрута. Отправленное вернуть нельзя.» Диалог отзыва: тот же, что в §17.7, плюс «и места потери GPS».

## 9. Чего НЕ делаем

- Не определяем и не утверждаем причину (глушение/тоннель/сбой), не называем виновных, не помечаем «спуфинг».
- Не отправляем треки, время, скорость, номера поездов; не отправляем «хорошие» ячейки; не строим по вкладам чьи-либо маршруты.
- Не предупреждаем голосом/звуком и не влияем на расчёты, запись «АВТО» и стоянки (слой только информационный).
- Не меняем старые эндпоинты, JSON-контракт, схему `Track.db`; не добавляем зависимости.
- Не делаем iOS/PWA в этой задаче (детектор и сетка в `commonMain` — готовы к переносу; тест-векторы сетки нужны PWA).
- Не показываем зоны без порога; не раскрываем точное число машинистов; не даём отозвать отправленное.
- Не используем зоны без GPS для проверки рабочего времени и ведомостей.

## 10. Этапы

1. (готово) Детектор + сетка + локальный слой + SCREEN_SPECS.
2. Сервер: миграция, `POST contrib`, `GET zones`, агрегатор, админка скрытия, тесты (дубль, порог 3 устройств / 2 дня, лимиты, 304, bbox).
3. Клиент: буфер сеанса, `GnssContribWorker`, кэш плиток, слияние, обновлённый текст согласия №2 (+ версия текста).
4. Поле: проверка на реальных поездках (Кириши), настройка порогов.

## 11. Решения, нужные от пользователя

1. **Сетка 250 м или ось (`axisHash` + км)?** Рекомендую сетку; но тогда текст согласия №2 («без координат») меняется. Принимаете расширение №2 или нужно отдельное согласие №3?
2. **Старые согласившиеся на №2**: показать один раз диалог с новой формулировкой (до «Согласен» зоны не отправляются, высоты идут как раньше) — подходит?
3. **Знаменатель «проехали чисто»**: не делать (v1: только число разных устройств ≥ 3 и ≥ 2 дней) — согласны? Иначе придётся слать «хорошие» ячейки.
4. **Пороги**: 3 устройства / 2 дня / окно 90 дней / ячейка 250 м / `tag` с ротацией 30 дней — утвердить или поправить.
5. **Кто может получать общую карту**: только вошедшие (рекомендую) / только давшие №2 («give-to-get») / все, в том числе без аккаунта? Учесть чувствительность публикации мест глушения.
6. **Локальный слой без согласия №1**: сейчас зон нет, пока нет треков (`Track.db` пишется только при №1). Хранить отдельный компактный реестр ячеек (новая БД, переживает удаление треков) или оставить как есть?
7. **Порог локального слоя**: сейчас показываем зону с первого случая (`tracks ≥ 1`, бледно); поднять до 2 поездок?
8. **Тап по пятну на самой линии пути** открывает карточку точки пути, а не зоны (пятно кликается вокруг линии). Устраивает или добавить строку «Здесь пропадал GPS» в карточку точки?
9. Нужно ли в v2 предупреждение «Впереди зона без GPS» при приближении (влияет на согласие и политику)?
