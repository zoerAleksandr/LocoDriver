# Хранение справки ВУ-45 — реализация (клиент готов, отправка за флагом)

Статус: **реализовано на клиенте** (ветка `feature/vu45`); сервер задеплоен (миграция 055, контракт - `docs/VU45_CERTIFICATES_API.md` репозитория сервера). Отправка на сервер ВКЛЮЧЕНА: `RemoteFeatureFlags.REMOTE_CERTIFICATES_ENABLED = true` (`data_remote`) после успешной сквозной проверки на локальном стенде (см. ниже).

## Что реализовано (отступления от первоначального проекта ниже)
- **Отдельная БД `BrakeCertificate.db`** (SQLDelight, как Track.db) вместо новой таблицы в Route.db: в Route.db сложная защищённая миграция/recovery, риск для всех пользователей. Таблица: certificate_id, route_id, train_id, updated_at, data (JSON), is_deleted.
- **Привязка к поезду** (решение владельца): одна текущая справка на (`routeId`, `trainId`); истории перевыдач нет; хранится всё, включая замеры и оборот.
- Domain: `brake/storage/BrakeCertificateStorage.kt` (`BrakeCertificateRepository`, `BrakeCertificateUseCase`, `BrakeCertificateMerge`, `BrakeCertificateSync`); `Route.brakeCertificates: List<BrakeCertificateSync>? = null`.
- Экран: загрузка при входе, автосохранение (debounce 1 с + при выходе), «Заполнить из маршрута» не затирает введённое (конфликты + «Заменить»).
- Удаление: поезд -> надгробие (уходит на сервер списком без него, затем purge), рейс -> удаление всех справок рейса.
- Синхронизация (`RoutesManager`/`SyncManager`): поле шлётся только при флаге true и если есть справки/надгробия; иначе поле отсутствует (null) - сервер не трогает справки. Слияние по LWW; пустой/отсутствующий ответ локальное не удаляет.
- Шаринг (`/v1/share/route`) справку не показывает. PWA и iOS - позже.

## Как проверено
- Сквозная проверка приложения (debug-сборка, флаг true) на ЛОКАЛЬНОМ стенде бэкенда, тестовый аккаунт: загрузка маршрута с поездом и локомотивом, «Заполнить из маршрута», ввод, синхронизация -> строка в `brake_certificate`; правка -> обновление на сервере (LWW); чистая установка + вход -> справка восстановлена с сервера; запрос старого клиента без поля и более старый `updatedAt` не стирают/не перезаписывают; ошибка сети - приложение не падает, справка сохранена локально и уходит при следующей синхронизации; удаление поезда -> справка удалена локально и на сервере; удаление рейса -> справки на сервере удалены (локально остаются, пока рейс в корзине; стираются при окончательном удалении). Найден и исправлен баг: правка одной справки не помечала рейс несинхронизированным и не уходила на сервер.
- Юнит-тесты `domain` (`BrakeCertificateStorageTest`: сохранение, LWW, удаление с поездом/рейсом, null vs [], сериализация Route со/без поля, разбор ответа GET) и `BrakeCertificateMappingTest`.
- Эмулятор: сохранение и восстановление после перезапуска, Route.db не тронут.
- Локальный стенд сервера (миграция 055): реальный JSON клиента (`Route` с `brakeCertificates`) -> POST принят; GET /v1/route/ вернул справку (второе устройство); POST без поля - справка сохранена; `[]` - стёрта; `isDeleted=true` - рейс и справки удалены (в таблице 0 строк). Приложение целиком к стенду не подключалось (флаг false), проверка на уровне контракта.

## 1. Что хранится

Одна справка = `BrakeCertificateData`:
- параметры расчёта (категория, спуск, автоблокировка, норма ручных осей), шапка (станция, время, дата, серия/номер локомотива, поезд №, вес, оси);
- нажатие: среднее на ось или строки «нажатие × оси»; локомотив в подсчёте (вес, оси, нажатие); «Другие данные» (К-xx, метки ЭПТ…, ТЦПВ, Встр., ДПВ, ВО2ХВ),
  нижняя часть (ручные оси, питательная сеть, напряжение, хвостовой вагон);
- замеры плотности (II, IV, «в пути»: секунды, ГР начало/конец, падение, зарядное давление, группа табл. 9.1, число локомотивов);
- оборот: список `TurnaroundEntry` (станция, класс стоянки >5/>30 мин, время прибытия/отправления, плотность, время готовности, табельный № вагонника, признак «авто»);
- `updatedAt` (мс) для LWW.
Не хранится: идущие секундомеры, UI-состояние, вкладка, раскрытые карточки.

## 2. Сущность и привязка

**Варианты.**
1. *Отдельная сущность `BrakeCertificate`, привязанная к рейсу (`routeId = BasicData.id`), 0..N на рейс (по одной на поезд/опробование).* — рекомендуется.
2. Поле внутри `Train` (JSON-колонка как `carInspector`) — проще, но справка живёт столько же, сколько поезд, и тянет за собой LWW всего поезда; в маршруте
   несколько поездов, а справка относится к конкретному составу.
3. Отдельная коллекция без рейса (`/v1/brake_certificates/`, как справочник напарников) — теряется связь «станции оборота ↔ поезд маршрута».

**Рекомендация: вариант 1.** Ключ — `certificateId` (UUID, клиент), внешняя ссылка — `routeId` (+ необязательный `trainId`). Справка не меняет расчёт зарплаты
и не входит в `Route`/`SyncData` по умолчанию: хранится как дочерняя коллекция рейса (как `partners`, `otherWorks`), удаление рейса удаляет справки.

## 3. Клиент: SQLDelight (RouteDatabase)

Новая таблица, аддитивная миграция `14.sqm` (текущая последняя — `13.sqm`):

```sql
CREATE TABLE IF NOT EXISTS BrakeCertificate (
    certificateId TEXT NOT NULL PRIMARY KEY,
    routeId       TEXT NOT NULL,            -- BasicData.id
    trainId       TEXT,
    payload       TEXT NOT NULL,            -- JSON BrakeCertificateData (целиком)
    updatedAt     INTEGER NOT NULL DEFAULT 0,
    isSynchronized INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_brakecert_route ON BrakeCertificate(routeId);
```

JSON-столбец — как `Train.stations`/`carInspector`: схема справки будет расти (новые поля) без новых миграций БД; в `BrakeCertificateData` все поля с значениями
по умолчанию и `ignoreUnknownKeys`. Миграция только добавляет таблицу — данные не теряются, старые версии БД открываются (SQLDelight проверяет версию схемы:
нужно поднять `version` и добавить `14.sqm`; откат приложения на старую версию после миграции невозможен — как для всех прежних миграций).
Репозиторий: `getByRoute(routeId)`, `upsert`, `deleteByRoute`; удаление рейса (в корзину/физически) каскадно (в коде, не FK).
Автосохранение — как формы (500 мс после изменения, финал в `onCleared`).

## 4. JSON-контракт (только аддитивно)

В `SyncData` (POST `/v1/route/`) — **новое необязательное поле** `brakeCertificates: Optional[List[Dict]] = None`, по образцу `otherWorks`/`partners`:
- `None` (поле не прислано — старый клиент) → сервер **не трогает** справки рейса;
- `[]` (новый клиент явно очистил) → full-replace удаляет все справки рейса;
- иначе full-replace по `certificateId`: что не упомянуто — удаляется.

Элемент массива (camelCase, время — Long мс, UUID клиента): `{certificateId, routeId?, trainId?, updatedAt, data: {…BrakeCertificateData…}}`.
`data` — непрозрачный JSON (сервер не разбирает поля справки, хранит как `JSONB`), поэтому новые поля в `BrakeCertificateData` не требуют изменения сервера.
Месяцы/даты без времени отсутствуют (дата справки — строка в `data`, не участвует в логике сервера). Старые клиенты игнорируют неизвестное поле в ответе GET.
Имена полей — camelCase (исключения snake_case контракта не затрагиваются). **Это изменение контракта: старые Android-клиенты не сломаются** (поле необязательное в обе стороны).

GET `/v1/route/` — в элемент рейса добавляется `brakeCertificates` (пусто = `[]`, как у `partners`; **не** 404). Баг контракта «404 при пустом списке рейсов» не копируется.

## 5. Семантика синхронизации

- Справка — дочерняя сущность рейса: уходит/приходит вместе с рейсом, `isSynchronized` рейса сбрасывается при изменении справки (как для поезда: `markUnsynchronizedAndTouch`).
- Конфликты: LWW по `updatedAt` справки внутри рейса (при расхождении побеждает больший `updatedAt`); full-replace коллекции на сервере по пришедшему списку.
- Удаление: удаление рейса удаляет справки (на клиенте и сервере, `delete_full_route`); удаление отдельной справки — исчезновение из списка в следующем POST (full-replace).
- Оборот не требует отдельной синхронизации: это часть `data`.

## 6. Сервер (репо `proxy-parser-nearest`, читать код: `pg_client.py`, `api/v1/route.py`, `schemas/response.py`)

- Модель `BrakeCertificate` (`models/brake_certificate.py`): `certificate_id UUID`, `route_id UUID FK route.id`, `train_id UUID NULL`, `user_id UUID FK user.id`,
  `payload JSONB NOT NULL`, `updated_at DOUBLE/BIGINT`. PK `(certificate_id, user_id)` — как `Partner` после миграции 033 (id придумывает клиент, у разных пользователей
  могут совпасть).
- Alembic: новая ревизия, **id ≤ 32 символов** (например `050_brake_certificate`), только `create_table` + индекс по `(route_id)`; применяется **вручную на проде ДО слияния кода**
  (CI-деплой не гоняет Alembic). Без изменения существующих таблиц.
- `route.py:save_data`: после блока partners — `if data.brakeCertificates is not None:` full-replace через `PostgresBrakeCertificateDbClient.process/delete_not_in_route`.
  Ownership: справка создаётся только для маршрута текущего пользователя — используется та же проверка владельца, что в `PostgresRouteDbClient.process`
  (`RouteOwnershipError` → 404); `user_id` берётся из токена, не из тела.
- Логи: **не логировать** `payload`, станции, табельные номера (PII); логировать только количество и id.
- Размер: ограничение длины `payload` (напр. 64 КБ на справку) и числа справок на рейс (напр. 20) → 422.

## 7. Влияние на PWA и iOS

- PWA (`loco-driver-pwa`, Vue): расчёт идёт через KMP-мост; `BrakeCertificateData` — в `domain` (commonMain), доступен мосту; UI справки PWA — отдельная задача. Пока PWA
  не знает поле, она не шлёт `brakeCertificates` → сервер не трогает справки (контракт `None`). **Важно:** PWA не должна слать `[]` без знания поля — иначе очистит справки.
- iOS: логика в `domain` готова; `Router.showBrakeCertificate` по умолчанию no-op; нужны SwiftUI-экран и вызов репозитория. Старый iOS-клиент поле не шлёт — безопасно.
