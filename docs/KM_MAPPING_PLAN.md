# Привязка GPS -> километр: план внедрения (по ANALYSIS_km_mapping.md, разд. 8-9)

## Что у нас уже есть (master)
- `domain/.../track/AltitudeContribution.kt`: `AxisPoint/SectionAxis/AxisProjector` - единственное место, где координаты трека
  сопоставляются с осью участка (вклад высот, согласие №2). Ось = накопленная длина полилинии (`geometry[].km` сервера) - тот же
  принцип, что у разобранного приложения. Было: полный перебор всех отрезков на каждую точку, метрика 111320 по обеим осям, порог
  боковой 30 м, нет окна/состояния.
- `domain/.../util/GnssPlausibility.kt`: фильтр подмены/скачков относительно прошлого принятого фикса (скорость 250/200 км/ч, прыжок
  >1 км за 30 с, сетевая позиция, выход из залипания по серии фиксов в новой области >= 5 за >= 60 с). Работает в записи трека
  ДО всякой привязки к оси.
- `domain/.../track/TrackAnalysis.kt` (`nearestOnTrack`, остановки), `util/ActualRails.kt`/`PathCleaner.kt`/`DriftFilter.kt`: привязка к
  собственным путям/рельсовой линии маршрута для карты, не к оси советника. Не трогаем.
- Станции: `axisKm/axisPicket` (км, пикет 1-10) - вводятся руками, формулы пикета в клиенте нет.
- `km_marks`, `KmMarks`, `kmrev`, калибровка: на клиенте НЕТ (km_marks только на сервере, `advisor_section`). `axisHash` ходит в вкладах
  высот (защита от смены геометрии). Ветки `feature/navigator`, `altitude-consent`, `gnss-zones-client`: тех же классов нет или
  они уже в master; живой привязки к оси нигде нет.

## Что внедряем (чистая логика, `domain/.../track/KmMapping.kt`, тесты `KmMappingTest`)
| Рекомендация | Статус | Заметка |
|---|---|---|
| 1. Окно ±250 вершин + полный перебор при d>200 м, плоская метрика, интерполяция | Сделано и ПОДКЛЮЧЕНО (`AxisLocator`, вклад высот) | Офлайн-обработка буфера, записи треков не касается. Флаг `AltitudeContribBuilder.WINDOWED_PROJECTION`. На обычных данных результат совпадает с полным перебором (тест), отличие только на параллельных путях <200 м |
| 2. Пороги точности 80/150 м до/после привязки | Сделано в `AxisTracker`, не подключено | Нужен потребитель (живой км на экране навигатора) |
| 3. Скачок: >500 м И >200 км/ч, dt>0.2 с, выход после 10 сбойных | Сделано в `AxisTracker` | В записи трека уже есть `GnssPlausibility`, он грубее (1 км/30 с) и работает до оси; два слоя не конфликтуют, но подключать второй в запись не нужно |
| 4. Вне маршрута: 3 подряд >200 м, события не писать | Сделано (`offRoute`, `eventsAllowed`) | Отличие от оригинала: далёкие фиксы не обновляют прошлую позицию/окно и не входят в проверку скачка; блокировка - только на 3-м подряд |
| 5. Пикет: floor(frac*n+1e-6) clamp, км=floor(x)+1 | Сделано (`Picket.of`) | Пример в разделе 7.4 анализа («5641.6 -> 5642 км 6 пк») противоречит формуле 8.4: по формуле 7 пк; следуем формуле/нашему «пк1 = первые 100 м» |
| 6. Слой нумерации: якоря, убывание, breaks как независимые куски, kmrev | Сделано (`RailKmMap`) | Экстраполяция за крайними якорями куска наклоном (в оригинале - зажим); split с константой 552 НЕ переносим (специфика их данных) |
| 7. Калибровка аддитивной поправкой | Сделано (`KmCalibration`), без хранилища/UI | Хранить отдельно от базы, привязывать к `axisHash` |
| 8. Гистерезис на стоянке | Сделано (`displayKmM`: speed<1 км/ч и сдвиг <30 м - км не меняется) | У оригинала нет |
| gcov (покрытие оси) | Не берём | В оригинале не читается; для нас нужен отдельный сигнал качества геометрии на сервере |

## Что не подключено и почему
`AxisTracker` ни в какой экран и ни в запись трека не вмешивается: запись в проде (`GpsRecordingService`, `GnssPlausibility`,
`TrackWriter`), живого потребителя «км по оси» ещё нет (навигатор - ветка `feature/navigator`, в master не сливается). Когда он
появится, подключать так: фиксы после `GnssPlausibility` -> `AxisTracker.onFix`; `displayKmM` -> `RailKmMap`/`KmCalibration` ->
`Picket.of`; `eventsAllowed=false` гасит запись событий остановок. Нумерации с сервера (`km_marks`) на клиенте ещё нет - контракт не менялся.
