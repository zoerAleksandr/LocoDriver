# План безопасного обновления и восстановления данных Android

Статус: этапы 0–1 реализованы и тестируются; этап 2 начат с versioned manifest;
локальный bootstrap, durable migration marker, candidate-миграция и fixtures
Room v1–v12 реализованы и проверены на Android 16
Ветка клиента: `codex/data-safety-diagnostics`  
Ветка сервера: `codex/data-safety-diagnostics-server`  
Область первой реализации: Android; iOS не затрагивается

## 1. Цель

После обновления приложения пользователь не должен терять маршруты из-за ошибки
локальной миграции. При неудаче приложение не падает циклически, а открывает
автономный экран восстановления. Для авторизованного пользователя восстановление
должно выполняться одной понятной кнопкой; технические шаги выполняются автоматически.

План не обещает невозможного: Android не даёт обычному приложению автоматически
откатить APK или гарантированно выполнить старый код перед внешним обновлением из
RuStore. Поэтому защищаем данные до миграции и заменяем локальную БД без переустановки
APK.

## 2. Проверенные факты

### 2.1. Подтверждено текущим кодом LocoDriver

1. `Route.db` создаётся в общем Koin-графе из `StartApp.onCreate()`.
2. `createRouteDriver()` уже делает локальную копию перед миграцией, проверяет
   результат, при ошибке восстанавливает старый файл и повторно бросает исключение.
3. Из-за повторного исключения отдельного рабочего recovery-режима сейчас нет:
   создание зависимостей, использующих `RouteDatabase`, может завершить запуск.
4. Локальный backup находится в приватном каталоге приложения. Он переживает обычное
   обновление APK, но не должен считаться переживающим удаление приложения.
5. Текущий `SyncWorker` отправляет только pending-изменения, требует токен и активный
   период подписки; это страховочная синхронизация, а не полная резервная копия.
6. Серверный `POST /v1/route/` использует full-replace дочерних коллекций. Обычная
   синхронизация не является неизменяемым снимком и может закрепить удаление.
7. В приложении включён Android Auto Backup, но XML-правила пока шаблонные и не
   определяют осознанный состав данных.
8. Основной API клиента сейчас указан как `http://87.228.110.32:8766/`. Передача
   резервных копий с пользовательскими данными через этот канал запрещается планом.
9. RuStore-код уже различает скачивание и завершение установки обновления через
   `completeUpdate()`, но этот путь работает только для обновления, инициированного
   внутри приложения.

### 2.2. Подтверждено документацией платформы

1. При обычном обновлении данные приватного каталога приложения сохраняются.
2. При удалении приложения app-specific storage удаляется, включая app-specific
   external storage.
3. Файл в общем хранилище через Storage Access Framework может пережить удаление,
   но Android показывает системный выбор места: полностью незаметно сделать это
   нельзя.
4. Android Auto Backup выполняется системой, имеет лимит 25 МБ, хранит последнюю
   копию и восстанавливает её при установке. Его время выполнения приложение не
   контролирует, поэтому это дополнительная, а не основная гарантия.
5. При flexible-обновлении RuStore приложение может получить состояние скачанного
   обновления и само вызвать завершение установки. Обновление напрямую из магазина
   не обязано запускать старую версию приложения перед установкой.

## 3. Что не входит в обещания системы

- автоматический откат на старую APK;
- гарантированный вызов приложения перед любым обновлением из магазина;
- гарантированное восстановление гостя после удаления приложения, если пользователь
  заранее не сохранил экспорт и не создал аккаунт;
- использование обычной синхронизации как полной копии всех локальных данных;
- отправка архивов по HTTP;
- удаление исходной/неудачно мигрированной БД до доказанного восстановления.

## 4. Рассмотренные варианты

| Вариант | Что сохраняет | После удаления APK | Автоматичность | Основной недостаток | Решение |
|---|---|---:|---:|---|---|
| Только локальная копия SQLite | Все локальные маршруты | Нет | Высокая | Удаляется вместе с приложением | Оставить как первый рубеж |
| Текущая серверная синхронизация | Только то, что успешно синхронизировано | Да | Средняя | Нет локальных pending; full-replace | Не считать backup |
| Неизменяемый серверный snapshot | Состав snapshot на момент создания | Да | Высокая | Нужны новый endpoint и хранилище | Базовый облачный рубеж |
| Логический клиентский архив | Все поддержанные сущности и версии | Да, если загружен | Высокая | Нужны versioned exporter/importer | Рекомендуемый формат |
| Зашифрованная сырая SQLite на сервере | Полный файл | Да | Высокая | Новая версия всё равно не умеет читать неизвестную старую схему | Только как forensic-копия |
| Экспорт через системный выбор файла | Все поддержанные данные | Да | Низкая | Требуется действие пользователя | Резервный путь для гостя |
| Android Auto Backup | Выбранные файлы до 25 МБ | Возможно | Системная | Нет гарантированного момента/наличия | Дополнительный рубеж |

### Выбор

Использовать многоуровневую схему:

1. локальный pre-migration backup;
2. миграция рабочей копии и атомарное переключение;
3. versioned логический recovery-архив для сервера;
4. неизменяемые серверные snapshots для авторизованных пользователей;
5. Android Auto Backup и ручной SAF-экспорт только как дополнительные рубежи.

Сырую SQLite можно временно хранить для диагностики, но нельзя считать переносимым
форматом восстановления.

## 5. Целевая архитектура

```text
Application.onCreate
        |
        v
RecoveryBootstrap (без RouteDatabase и общего Koin-графа)
        |
        +-- READY ----------------------> обычный Koin -> MainActivity
        |
        +-- MIGRATION_REQUIRED
        |       -> checkpoint -> backup -> migrate copy -> validate -> atomic swap
        |                                                |
        |                          success --------------+
        |                          failure -> RECOVERY_REQUIRED
        |
        +-- RECOVERY_REQUIRED ----------> RecoveryActivity
                                              |
                  +---------------------------+-----------------------+
                  |                           |                       |
             local backup              cloud snapshot          SAF archive
                  |                           |                       |
                  +----------> fresh current DB <--------------------+
                                   |
                             validate + commit
                                   |
                            ordinary app startup
```

### 5.1. Независимый bootstrap

До запуска общего Koin-графа создаётся минимальный `RecoveryBootstrap`. Он имеет
доступ только к:

- `SharedPreferences` с recovery-состоянием;
- файловой системе и метаданным БД;
- минимальному HTTP-клиенту восстановления;
- безопасному хранилищу токена;
- коду входа/регистрации, не использующему `RouteDatabase`.

Он возвращает одно из состояний:

- `READY`;
- `MIGRATION_IN_PROGRESS` (перезапуск после прерывания);
- `RECOVERY_REQUIRED`;
- `RECOVERY_IN_PROGRESS`;
- `BLOCKED_LOW_STORAGE`.

Если состояние не `READY`, обычный граф с `RouteDatabase` не создаётся. Это устраняет
цикл «миграция упала — DI упал — приложение снова упало».

### 5.2. Безопасная миграция

1. Захватить process-level lock миграции.
2. Проверить свободное место: минимум размер БД × 3 плюс фиксированный запас.
3. Выполнить WAL checkpoint и закрыть все соединения.
4. Записать durable marker с исходной/целевой версией и стадией.
5. Создать `source.backup`, включая согласованное состояние WAL.
6. Проверить `PRAGMA integrity_check` копии.
7. Мигрировать отдельный `candidate.db`, а не рабочий файл.
8. Проверить схему, целостность, ID маршрутов, pending-маршруты, дочерние записи,
   orphan-записи и допустимые изменения конкретной миграции.
9. Синхронизировать файл на диск и атомарно заменить рабочую БД.
10. Выполнить пробное открытие текущим SQLDelight-драйвером.
11. Только после успешного запуска отметить миграцию завершённой.

При ошибке рабочая БД не заменяется. Сохраняются source backup, candidate и marker;
показывается recovery-экран. Автоматическое повторение той же миграции блокируется
по ключу `sourceVersion + targetVersion + appBuild`, пока пользователь не выберет
«Повторить» или не установит исправленную сборку.

### 5.3. Формат recovery-архива

Архив — не дамп таблиц и не `SyncData`, а отдельный контракт:

```text
manifest.json
  archiveFormatVersion
  sourceDbVersion
  appBuild
  createdAt
  installationId
  accountIdHash (только для локальной сверки; не email)
  sections[]: name, itemCount, sha256

routes.ndjson
settings.json
salary-settings.json
norms.json
attachments-manifest.json
```

Требования:

- контракт аддитивный: неизвестные поля игнорируются;
- обязательная версия формата и контрольные суммы;
- UUID, время и 0-based month сохраняют текущую контрактную семантику;
- удалённые/корзинные и несинхронизированные маршруты включаются;
- диагностические события и токены не входят;
- импорт всегда идёт в свежую БД текущей схемы;
- для каждой поддерживаемой старой схемы существует отдельный reader/mapper;
- отсутствие reader для версии не приводит к удалению исходника.

### 5.4. Почему нужен versioned reader

Если миграция уже сломалась, текущие SQLDelight-запросы могут не открыть старую БД.
Поэтому exporter читает её через SQLite metadata (`user_version`, `sqlite_master`,
`PRAGMA table_info`) и явные адаптеры известных версий. Нельзя «угадать» отсутствующие
поля: для каждого поля задаётся документированное правило — прочитать, вычислить
без потери смысла либо отметить как отсутствующее.

## 6. Серверное восстановление

### 6.1. Новый контракт (только аддитивные endpoint'ы)

Предлагаемый набор:

```http
POST   /v1/recovery/snapshots
PUT    /v1/recovery/snapshots/{snapshotId}/parts/{partNumber}
POST   /v1/recovery/snapshots/{snapshotId}/complete
GET    /v1/recovery/snapshots/latest
GET    /v1/recovery/snapshots/{snapshotId}/manifest
GET    /v1/recovery/snapshots/{snapshotId}/download
POST   /v1/recovery/snapshots/{snapshotId}/restored
```

Все endpoint'ы требуют JWT. `user_id` берётся только из проверенного токена, никогда
из body. Snapshot принадлежит одному пользователю; запрос чужого ID возвращает 404.
Повторная загрузка использует `idempotencyKey` и не создаёт дубликаты.

До реализации размеры реальных БД нужно измерить обезличенным агрегатом. Если архивы
гарантированно малы, chunk upload можно отложить и начать с одного streaming upload;
контракт частей не следует добавлять без необходимости.

### 6.2. Серверная модель

`recovery_snapshot`:

- `id`, `user_id`, `installation_id`;
- `archive_format_version`, `source_db_version`, `app_build`;
- `status`: `UPLOADING`, `READY`, `INVALID`, `RESTORED`, `EXPIRED`;
- `size_bytes`, `sha256`, `object_key`;
- `created_at`, `completed_at`, `restored_at`, `expires_at`;
- `idempotency_key` с unique `(user_id, idempotency_key)`.

Содержимое хранится не в PostgreSQL, а в закрытом object storage либо защищённом
файловом хранилище с отдельным backup. PostgreSQL хранит метаданные. Публичных URL
нет; выдача идёт только после проверки владельца.

### 6.3. Когда создавать snapshot

- после успешной полной синхронизации, если локальные pending отсутствуют;
- перед миграцией — обязательно попытаться создать свежий snapshot, если пользователь
  авторизован и сеть доступна;
- при наличии pending — загрузить полный recovery-архив, а не только серверное
  состояние;
- если сети нет, не блокировать миграцию при наличии проверенной локальной копии,
  но явно сохранить состояние `cloudBackupPending`;
- обновление через встроенный RuStore flow не завершать до успешного локального
  backup; облачный upload ждать только в пределах ограниченного таймаута, затем
  оставить WorkManager-задачу.

Внешнее обновление RuStore покрывается тем, что backup создаёт уже новая версия
непосредственно перед миграцией. Для него нельзя обещать предзагрузку старой версией.

## 7. Экран восстановления

Экран открывается даже при неработоспособной `Route.db`. Основная кнопка:

> Восстановить приложение

Фактически она не переустанавливает APK. Она автоматически:

1. определяет доступные источники;
2. проверяет локальный backup;
3. при авторизации сверяет/скачивает серверный snapshot;
4. выбирает наиболее полный источник без молчаливого предпочтения более старой копии;
5. создаёт свежую БД текущей схемы;
6. импортирует данные;
7. проверяет количество и ID маршрутов, pending и дочерние записи;
8. атомарно переключает БД;
9. запускает обычное приложение.

Пользователь видит источник и дату: «Локальная копия, сегодня 14:32» или «Облачная
копия, вчера 22:10». Если источники отличаются, приложение не объединяет данные
наугад: выполняет детерминированное сравнение по route ID и `updatedAt`; конфликтные
маршруты сохраняет как две копии либо просит выбор после восстановления.

Дополнительные действия:

- «Повторить миграцию» — только явное действие;
- «Войти и восстановить» / «Создать аккаунт и сохранить данные»;
- «Выбрать файл резервной копии»;
- «Экспортировать копию»;
- «Связаться с поддержкой» с диагностическим кодом.

Кнопка «Начать с пустой базы» помещается в отдельный опасный сценарий. Перед ней
обязательно сохраняется доступный архив; исходные файлы не удаляются.

## 8. Матрица пользовательских сценариев

| Сценарий | Поведение |
|---|---|
| Миграция успешна | Candidate проверяется и становится рабочей БД; backup сохраняется до контрольного срока |
| Ошибка, пользователь авторизован и онлайн | Recovery screen; одна кнопка выбирает полный локальный архив или облачный snapshot и восстанавливает |
| Ошибка, авторизован, но офлайн | Восстановление из локальной копии; облачная сверка после запуска |
| Ошибка, гость онлайн | Предложить вход/регистрацию без открытия Route.db; после входа загрузить/восстановить архив |
| Ошибка, гость офлайн | Восстановить локально; сохранить экспорт через SAF; не требовать аккаунт для доступа к своим локальным данным |
| Обновление начато внутри приложения | Локальный backup обязателен до `completeUpdate()`; облачная копия best effort с таймаутом |
| Обновление напрямую в RuStore | Новая версия делает backup перед первой миграцией |
| Процесс убит во время миграции | Marker указывает стадию; рабочая БД не заменена; bootstrap продолжает/отменяет candidate безопасно |
| Процесс убит при восстановлении | Импорт идёт в новый файл; повторный запуск продолжает с idempotent marker |
| Сервер недоступен | Локальный путь остаётся доступен, upload повторяется с backoff |
| Недостаточно места | Миграция не начинается; показывается требуемый объём, исходник не меняется |
| Snapshot повреждён | Не импортировать; попробовать другой источник; сохранить исходник |
| Токен истёк | Recovery login обновляет авторизацию без Route.db |
| Удаление и новая установка | Для аккаунта — загрузка snapshot после входа; для гостя — только Android Backup или выбранный им SAF-файл |

## 9. Безопасность и приватность

Обязательные условия до включения облачного recovery:

1. Перевести recovery API на HTTPS с проверкой сертификата. HTTP запрещён.
2. Не помещать токены, email, `vk_id` и пароль в архив или логи.
3. Проверять владельца snapshot на каждой операции; не доверять `user_id` клиента.
4. Шифровать хранилище сервера и его резервные копии; ключи отделить от данных.
5. Ограничить размер, число частей, частоту запросов и объём на пользователя.
6. Проверять checksum до пометки `READY` и после скачивания.
7. Не распаковывать пути из пользовательского архива; использовать фиксированные
   имена секций и streaming parser.
8. Не использовать diagnostic endpoint для пользовательских данных.
9. Логировать только snapshot ID, размер, версии, статус и технический reason code.
10. Определить срок хранения и удалить данные по запросу пользователя.

Клиентское end-to-end шифрование не выбирается автоматически: после удаления
приложения локальный ключ может исчезнуть, а серверный ключ делает схему не E2E.
Если потребуется E2E, сначала нужен отдельный продуктовый выбор способа восстановления
ключа (пароль/фраза/системный аккаунт), иначе «одно нажатие» не гарантируется.

## 10. Совместимость со старыми клиентами

- существующие `/v1/route`, auth и settings контракты не меняются;
- recovery добавляется отдельными endpoint'ами и таблицами;
- сервер сначала выкатывается без обязательного использования recovery;
- старые клиенты продолжают синхронизацию как раньше;
- новые серверные Pydantic-схемы принимают дополнительные поля по принятой политике;
- feature flag позволяет выключить upload/download без отката клиента;
- новая версия клиента понимает отсутствие endpoint (`404/501`) как «облако пока
  недоступно» и сохраняет локальный recovery;
- очистка snapshots никогда не вызывает удаление обычных серверных маршрутов.

## 11. Порядок реализации

### Этап 0. Измерения и фиксация контрактов

- собрать размер Route/Settings/Salary БД, число записей и распределение версий без PII;
- составить карту всех SQLDelight/legacy версий, которые реально могли попасть в релиз;
- сохранить тестовые обезличенные fixtures каждой версии;
- определить максимальный поддерживаемый размер и срок хранения;
- проверить HTTPS-домен и сертификат для API.

Стоп-критерий: без карты старых схем нельзя писать «универсальный» importer.

### Этап 1. Bootstrap и безопасная локальная миграция

- вынести проверку состояния до общего Koin;
- добавить recovery marker/state machine;
- мигрировать candidate-файл и делать атомарное переключение;
- реализовать независимый RecoveryActivity;
- заблокировать автоматический retry известной упавшей миграции;
- оставить существующую БД и backup неизменными при любой ошибке.

Реализовано: durable marker записывает стадии `BACKUP_READY`,
`CANDIDATE_COPYING`, `CANDIDATE_MIGRATING`, `CANDIDATE_VALIDATED`, `SWAPPING`,
`SWAPPED`, `SUCCEEDED` и `FAILED` синхронным `commit()`. При перезапуске после
нетерминальной стадии удаляются только disposable candidate-файлы. Исходная БД
мигрируется заново либо уже атомарно установленная и валидная текущая БД принимается
без повторного изменения.

Перед backup выполняется проверка свободного места: не менее трёх размеров текущей
`Route.db` плюс 16 МБ резерва. При нехватке места миграция не начинается, а recovery
экран просит освободить накопитель. Межпроцессная файловая блокировка не допускает
двух одновременных миграций одной базы; конкурентная попытка не изменяет исходник.
Instrumentation-тест отдельно воспроизводит committed-запись, находящуюся только в
WAL после аварийного завершения; checkpoint, backup и миграция сохраняют её.
Для всех предмиграционных открытий `Route.db` отключён стандартный Android
corruption handler, способный удалить распознанную повреждённую БД. При ошибке файл
и существующий backup сохраняются байт-в-байт, candidate не создаётся, а bootstrap
переходит в recovery mode.
Отдельно проверены объёмный fixture (500 маршрутов и 2000 дочерних записей) и база
с существующим legacy orphan. Большой набор сохраняется полностью; старый orphan
не блокирует доступ к остальным маршрутам и не размножается при миграции.
Bootstrap integration-тест подтверждает: после ошибки та же сборка не повторяет
миграцию автоматически, явное действие пользователя разрешает retry, а следующая
сборка получает одну автоматическую попытку. Отсутствие любой обязательной таблицы
`BasicData`, `Locomotive`, `Train`, `Passenger` или `Photo` считается неизвестным
повреждением и не маскируется созданием пустой таблицы.
Финализация новой предмиграционной копии и восстановление рабочей БД выполняются
через `rename(2)` на том же filesystem. Старая копия остаётся целой до единственной
атомарной замены; backup никогда не копируется прямо поверх `Route.db`. Остаточные
`candidate`/`restore.tmp`/`pre_migration.tmp` считаются disposable и очищаются под
межпроцессной блокировкой при следующем запуске.
Перед каждым атомарным переключением содержимое временного файла принудительно
синхронизируется через `fsync`; после `rename(2)` синхронизируется родительский
каталог. Это закрывает окно потери уже переименованного файла при внезапном
выключении устройства, а не только при остановке процесса.

### Этап 2. Логический exporter/importer

- зафиксировать `archiveFormatVersion=1`;
- написать reader для каждой подтверждённой схемы;
- импортировать в свежую текущую БД;
- добавить checksums, count/ID validation и conflict policy;
- добавить ручной SAF export/import.

Начато: зафиксирован сериализуемый `archiveFormatVersion=1` и пять обязательных
секций. Общий KMP-валидатор проверяет версию, метаданные, безопасные имена без путей,
уникальность и наличие секций, неотрицательные counts, формат SHA-256 и совпадение
фактических digest/count. Неизвестные безопасно названные дополнительные секции не
мешают forward compatibility, но importer будет читать только известную allow-list.
Manifest ограничен 64 КиБ и 32 секциями до импорта; длины идентификаторов также
ограничены. SHA-256 реализован в общем KMP-коде и проверен стандартными тестовыми
векторами, поэтому Android и iOS вычисляют одинаковые digest без `java.*` в
`commonMain`.
Реализован первый Android exporter `routes.ndjson`: он открывает старую `Route.db`
только read-only с недеструктивным corruption handler, выдаёт по одной строке на
маршрут в стабильном порядке и включает строки `BasicData`, `Locomotive`, `Train`,
`Passenger`, `OtherWork`, `RoutePartner`, `Photo` по allow-list. SQLite BLOB в v1
отклоняется явно. Секция пишется во временный файл, синхронизируется и атомарно
заменяет предыдущую; потоковый digest совпадает с общей KMP SHA-256 реализацией.
Exporter проверен напрямую на заполненных Room v1–v12 до миграции. Если обнаружены
legacy orphan-строки, `routes.ndjson` не финализируется: до появления отдельного
lossless-формата для таких строк безопаснее явно отложить облачный snapshot, чем
молча объявить неполный архив успешным. Исходная БД при этом остаётся read-only.
Добавлен общий KMP reader/validator одной NDJSON-записи. До будущего импорта он
ограничивает строку 2 МиБ и 10 000 строками сущностей на маршрут, принимает только
семь известных таблиц, проверяет безопасные имена колонок, наличие пяти базовых
таблиц, ровно одну `BasicData`, соответствие `id/basicId` route ID и уникальность
первичных ключей. Экспорт Room v1–v12 проходит этот reader без послаблений.

### Этап 3. Сервер snapshots

- добавить модели, миграцию, owner-only API, идемпотентность и лимиты;
- подключить закрытое storage и retention job;
- добавить health/metrics без PII;
- покрыть API тестами IDOR, повреждения, retry и конкурентной загрузки.

### Этап 4. Клиентское облачное восстановление

- минимальный recovery HTTP/auth graph;
- автоматический snapshot после безопасных точек;
- кнопка одного нажатия и resumable download/upload;
- WorkManager retry с exponential backoff;
- интеграция с RuStore `completeUpdate()` без зависимости от неё.

### Этап 5. Наблюдение и постепенное включение

1. Сервер и HTTPS, feature flag выключен.
2. Клиент пишет только локальные markers и проверяет candidate.
3. Включить upload для внутренней группы.
4. Проверить restore-drill на реальных обезличенных размерах.
5. Включить небольшой процент production.
6. Увеличивать охват только при отсутствии потерь и росте успешных восстановлений.

## 12. Тестирование

### Unit

- state machine и все переходы после process death;
- versioned readers и default/missing-field rules;
- checksum, manifest validation, размер/лимиты;
- выбор источника и конфликтная политика;
- блокировка повторной упавшей миграции.

### Миграционные fixtures

Для каждой выпущенной версии БД:

- успешный путь до current;
- отсутствие каждой опциональной колонки;
- WAL с незачекпойнченными изменениями;
- частично повреждённая БД;
- orphan-записи;
- пустая, большая и содержащая pending/корзинные маршруты БД;
- kill процесса на каждой стадии.

### Сервер

- старый клиент продолжает работать без изменений;
- чужой snapshot всегда 404;
- повтор idempotency key возвращает тот же результат;
- конкурентный complete безопасен;
- превышение размера/rate limit отклоняется;
- corrupted checksum не получает `READY`;
- expired snapshot недоступен после retention.

### End-to-end

- обновление через ADB/RuStore-equivalent с каждой поддержанной БД;
- ошибка миграции -> recovery screen, а не crash loop;
- восстановление локально, из облака и SAF;
- офлайн -> перезапуск -> онлайн;
- истёкший токен -> login -> restore;
- удаление приложения -> установка -> вход -> cloud restore;
- отсутствие recovery endpoint не мешает локальному запуску.

## 13. Наблюдаемость

В уже созданную обезличенную диагностику добавить только технические события:

- `RECOVERY_MODE_ENTERED`;
- `RECOVERY_SOURCE_SELECTED` (LOCAL/CLOUD/SAF без содержимого);
- `RECOVERY_SUCCEEDED`;
- `RECOVERY_FAILED` с enum reason;
- `SNAPSHOT_UPLOAD_SUCCEEDED/FAILED`;
- размеры в диапазонах, а не точные пользовательские данные.

В кабинете показывать версии source/target, длительность, reason code, количество
успехов/ошибок. Не показывать содержимое маршрутов.

Алерты:

- доля rollback/recovery по версии приложения;
- restore success rate;
- snapshots stuck в `UPLOADING`;
- checksum failures;
- рост `BLOCKED_LOW_STORAGE`;
- любой IDOR/security отказ отдельным счётчиком без PII.

## 14. Retention и очистка

Рекомендуемые начальные значения, требующие продуктового подтверждения после замеров:

- локальный последний успешный backup: до следующей подтверждённой миграции, минимум
  30 дней;
- локальная failed candidate: 14 дней либо ручной экспорт;
- серверные snapshots: последние 3 успешных и минимум 90 дней;
- незавершённые uploads: 24 часа;
- удаление snapshot не удаляет маршруты и не связано с корзиной маршрутов.

Это предложения, а не проверенные текущие требования.

## 15. Критерии готовности к production

- все реально выпущенные версии схемы имеют fixture и reader;
- migration/restore tests проходят для каждой версии;
- процесс можно убить на любой стадии без потери исходника;
- старый production-клиент проходит contract tests с новым сервером;
- recovery API работает только по HTTPS;
- restore-drill подтверждает восстановление IDs, pending и дочерних записей;
- нет логов с токенами/PII/маршрутами;
- feature flag и server-side kill switch проверены;
- кабинет показывает rollout и ошибки;
- документированы поддержка и безопасный ручной путь;
- только после этого разрешается автоочистка старых recovery-файлов.

## 16. Решения, которые нужно зафиксировать перед кодом

Рекомендуемые значения указаны, но не выдаются за согласованные:

1. Срок/число серверных snapshots: рекомендуется 3 копии и 90 дней.
2. Входит ли backup в подписку: рекомендуется защита данных для всех аккаунтов,
   независимо от подписки.
3. Максимальный размер: определить только после этапа измерений.
4. Хранилище сервера: выбрать после проверки доступной инфраструктуры и backup.
5. Конфликты: рекомендуется сохранять обе версии, а не молча выбирать одну.
6. Гость: локальное восстановление доступно всегда; аккаунт предлагается, но не
   блокирует доступ к сохранившейся локальной копии.
7. E2E-шифрование: не включать, пока не выбран восстанавливаемый ключевой UX.

## 17. Что пересмотреть при росте

- перейти со streaming upload на multipart только при подтверждённых размерах;
- вынести snapshots в отдельный сервис при росте нагрузки;
- добавить дедупликацию блоков только после измерения стоимости storage;
- расширить recovery на iOS отдельным проектом после стабилизации Android;
- пересмотреть retention по фактической частоте восстановлений и требованиям
  приватности.

## 18. Точка начала следующего этапа

После утверждения этого плана реализация начинается не с server upload, а с этапа 0:
инвентаризации реально выпущенных схем и создания миграционных fixtures. Затем —
независимый bootstrap и проверяемая локальная миграция. Это даёт защиту даже до
включения облака и не меняет существующие JSON-контракты.
